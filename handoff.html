Fanfic Reader — Handoff & Migration Notes

Front-end redesign of the Character.ai fanfic reader · June 2026

branch: 0612-handoff compare against: main

This branch is a visual redesign of the reader front-end. Everything here is presentation — the underlying content model and filtering logic are unchanged.

What changed

1 · Two ways to view every story — image vs list biggest change

This is the largest departure from main. Every work now renders through one of two brand-new card components, and the whole site flips between them:

  • Image view — a full-bleed cover card (the artwork carries it).
  • List view — a dense, text-first card (title, author, tags, stats) with no image.

The same two components are reused everywhere works appear — the home shelves, the browse results, and the library — so the look stays consistent across the site. This replaces the single card style that exists on main.

2 · Home page (Discover)

The landing page was rebuilt as a browsable, editorial home that sits on top of the existing filter engine — nothing about how works are filtered or loaded changed underneath it.

  • A rotating hero banner at the top.
  • Horizontal “shelves” (Trending, Featured) and a Creators row, each swipeable with arrow buttons.
  • A “Continue Reading” row driven by the reader’s saved progress.

3 · Visual / Text mode toggle

A floating toggle in the bottom-right is what flips the whole site between the image view and the list view (above). Switching plays a brief full-screen colour sweep (a small WebGL animation) as the transition, replacing the old grey loading placeholders.

4 · Reading page

  • The work header was reordered to a clear hierarchy: cover → tags/badges → title → author (with photo) → description → stats. This same hierarchy is now used consistently across the entire site — the cards and the story-info pop-up follow it too.
  • Each chapter shows a small author line (work title · author) so a reader who lands deep in a story still sees who wrote it.
  • The “story info” pop-up now mirrors that same header layout.
  • Spacing and font sizes were aligned between the header, the cards, and the pop-up.

5 · Search, filters & navigation polish

  • Refined the search dropdown and the sort menu (padding, rounded corners, consistent widths).
  • Centered the top navigation; renamed the first nav item to “Stories.”

6 · Cleanup

Removed unused components and the old loading-placeholder code path that the new transition made obsolete. No behaviour was lost — verified with a full production build.

How to migrate

This is a static Next.js 15 front-end — no database or API in this repo. Every story is a Markdown file in content/works, and reader state (progress, preferences, mode) lives in browser local storage. An authentic migration is mostly about connecting these surfaces to your real data. Hand the prompt below to your coding agent to drive it:

Prompt for your coding agentYou are migrating a front-end redesign into our codebase. The redesign is on branch `0612-handoff`; our current production version is `main`. 1. Diff `0612-handoff` against `main` to get the full, file-level scope of the change. Treat that diff as the source of truth. 2. The redesign is presentation-only — do not change how our data is fetched or filtered, only re-wire the new UI to our real sources. 3. Replace the sample/placeholder data with our real backend: - Comments, the signed-in user's library/bookmarks, and recommendations are dummy data. Locate them via the `@DUMMY` and `@TODO-DEV` markers in the code and the notes in `.claude/docs/wiring-guide.md` and `.claude/docs/api-contracts.md`. Point them at our APIs, keeping the documented data shapes. - Reading progress, preferences, and the visual/text mode are stored in browser local storage with no auth. Move per-user state onto our authentication + persistence. 4. Swap the placeholder images in `public/` (covers, hero banners, fandom art, the author photo placeholder) for real assets. 5. The mode-switch animation uses a third-party package, `glimm` (proprietary licence, single maintainer). Decide whether to keep it or replace it with a CSS transition — it is used only in `src/app/layout.tsx` and the mode toggle. 6. Run `npm install && npm run build` on Node 22 and confirm a clean build before opening your PR.
Note on the glimm dependency. The colour-sweep transition relies on a small, newly-published, single-maintainer package published under a proprietary (all-rights-reserved) licence. Confirm the licence is acceptable for your distribution before shipping. It’s used in only two places, so it’s straightforward to swap for a CSS transition or remove.

Run it
